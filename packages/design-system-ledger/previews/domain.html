The requirement checklist

Rows and progress.lg-req-row · .lg-checklist-progress

The status a row shows is its current version's status, resolved through requirements.current_version_id at read time. Storing effective status on the requirement is forbidden, so the component takes it as a prop and assumes a join produced it. Progress is drawn as one segment per requirement rather than a filled bar: a bar implies a single ordered quantity, and a checklist is a set of independent outcomes, so three coming back negative is not "60% done".

Archiving is orthogonal to status[data-archived]

Look at the last row above. Its title dims, but nothing is struck through and no history is hidden. A requirement can be archived whatever its verification history, and archiving says nothing about whether it was ever verified, so suppressing that history would be a lie of omission. The archived chip is dashed rather than tinted, so it can never be read as a fourth verdict.

Verdicts

A negative verdict is not an error.lg-verdict-card

The single most important rendering decision in this system. requirement_versions.status stores a negative verdict as eval_failed, a column name that reads like a malfunction and is not one: per the transition table, the Evaluator returning "not satisfied" is what writes it. So it renders as "Not satisfied" in solid ink, never in red, and the raw enum name never reaches a screen. Red is reserved for the run not finishing at all, which says nothing about the code. Note also that both cards carry a tinted hairline and nothing more: no surface here gets a coloured side tab.

The headline verdict on a stakeholder's report view, and the reason this direction carries a display type size at all. The negative one is set in plain ink rather than tinted: it does not need a hue to be emphatic, and giving it one would put it next to the red this system reserves for things that actually broke.

Rationales are prose, never code.lg-verdict-card__rationale

The Evaluator is constrained at generation time never to emit verbatim source; it may cite a path or a line range, which is what the file reference below is for. The rationale is therefore styled as prose at a 66-character measure, so a leak would render as visibly wrong. That is a weak but free signal and not a filter, because filtering code out of already-generated text is unreliable, which is why the constraint lives in the agent's output step instead.

Evidence and the log

Sealed is not unverifiable.lg-evidence

Two things land at once here. The bundle's contents are not viewable, because it holds real source from a private repo and no disclosure mechanism exists in this phase. Its digest is still independently checkable, because verifying that evidence was never altered and disclosing what it says are separate operations, and the first never requires the second. So the verify action stays live, as a real secondary button rather than a greyed-out hint. Removing it because the bundle is private would collapse the distinction the whole trust model rests on.

An intact record is not a correct judgment.lg-logref

The most dangerous surface in the product to get wrong. An inclusion proof shows the record was not quietly altered after it was written, and says nothing about whether the Evaluator reached the right conclusion. Two things enforce that: the caveat is not an optional prop, it comes from a map keyed by state so no call site can drop it, and a valid proof renders in plain ink rather than the satisfied green, because reusing the verdict colour would fuse the two claims.

Never fake a progress percentage.lg-eval

Evaluation runs synchronously inside the request that submits the claim, so the developer's own tab is held open for its full duration. The bar is indeterminate because there is no honest fraction for an LLM evaluation, and a fabricated percentage is the kind of small lie that costs a user their trust in everything else on the page. The clock turns ochre past 70% of the ceiling so the developer is warned before the request is cut off rather than after, and ochre is not a verdict colour, so it cannot be misread as a result.

The undo window is the whole reversible window.lg-countdown

Repo attachment is permanent once this window closes: there is no detach endpoint and no soft-delete state, so the countdown is the entire reversible period. That is why the remaining time is drawn as a ring and printed as a number inside it, rather than implied by a toast that fades over a duration the user has to guess.
